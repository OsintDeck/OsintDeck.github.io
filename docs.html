Introducción y propósito

Qué es este documento. Un manual lineal pensado para que cualquier persona con rol en el proyecto encuentre respuestas sin adivinar el orden: primero instalación y publicación, después integraciones (Google, Cloudflare, reportes), luego por qué el software está construido así (arquitectura y motor) y al final referencia (AJAX, cron, tablas). La sección Estructura del manual y recorridos amplía esta lógica con tablas y rutas por rol.

OSINT (Open Source Intelligence) designa el aprovechamiento metódico de información de fuentes abiertas y legalmente accesibles. OSINT Deck es un plugin de WordPress que implementa un panel centralizado (deck): un único punto de interacción donde el analista ingresa datos, filtra el catálogo y abre herramientas externas con parámetros ya resueltos, reduciendo el costo de cambiar de contexto entre docenas de pestañas.

Arquitectónicamente se comporta como un framework modular orientado a investigadores, periodistas y equipos de ciberseguridad: el núcleo orquesta detección de tipos de entrada, selección de herramientas, persistencia en base de datos y superficies de administración y front-end sin acoplar la lógica a un tema concreto de WordPress.

Contexto institucional. El desarrollo se enmarca en la Licenciatura en Ciberseguridad de la Universidad Nacional Raúl Scalabrini Ortiz (UNSO), ubicada en San Isidro, Buenos Aires, Argentina, su sitio web es https://www.unso.edu.ar/ y toma como referencia de dominio la experiencia del sitio OSINT.com.ar. El software se distribuye bajo licencia libre; el cuerpo del manual prioriza implementación y operación en lenguaje claro, con detalle técnico donde hace falta.

Guía rápida: ¿por dónde empiezo?

En esta sección. Secuencia mínima para pasar de “no tengo nada” a “el mazo visible en una página”. Antes: leé Estructura del manual si no sabés por dónde seguir. Después: Tener WordPress → ZIP → Web pública.

Si nunca instalaste un plugin o WordPress te suena nuevo, seguí esta lista en orden:

  1. WordPress funcionando: tu sitio ya debe estar instalado (hosting local o en Internet). Si no, leé la sección Tener WordPress instalado.
  2. Subir OSINT Deck: con un archivo ZIP del plugin, desde el escritorio de WordPress. Los pasos detallados están en Instalar el plugin (modo fácil).
  3. Activar el plugin: un clic en Activar. Si algo falla, WordPress suele mostrar un mensaje en rojo: copialo tal cual para soporte.
  4. Poner el mazo en una página: editás una página o entrada y pegás el shortcode [osint_deck] (o [osint_deck_search]). Guardás y visitás la página: debería aparecer la barra de búsqueda del mazo.
  5. Configurar (opcional): en el menú lateral izquierdo del escritorio: OSINT Deck → distintas secciones según lo que quieras ajustar (textos, tema, herramientas, etc.).
Tip: Descargá siempre el ZIP desde las Releases de GitHub (incluye la carpeta vendor/ lista para usar). Así no necesitás Composer en el servidor.

Tener WordPress instalado (antes del plugin)

OSINT Deck es un plugin: vive dentro de un sitio WordPress. No reemplaza a WordPress ni se instala “solo”: primero tenés que tener WordPress en marcha (base de datos, archivos en el servidor, acceso al escritorio /wp-admin).

Instalar OSINT Deck (modo fácil, sin terminal)

Estos pasos son para quien ya tiene WordPress y sólo quiere añadir el plugin.

1. Conseguir el archivo ZIP del plugin

  • Entrá a la sección Releases del repositorio OsintDeck/OsintDeck en GitHub (acceso directo a las descargas).
  • Descargá el último ZIP publicado (nombre similar a osint-deck-vX.Y.Z.zip). Ese paquete está pensado para instalarse en WordPress e incluye las dependencias PHP (vendor/).
  • No descomprimas el ZIP en tu PC para subir carpeta por carpeta: WordPress espera un único archivo .zip en el paso de subida.

2. Subir el plugin desde WordPress

  1. Iniciá sesión en el escritorio: normalmente https://tu-dominio.com/wp-admin.
  2. Menú izquierdo: Plugins → Añadir nuevo plugin.
  3. Pulsá el botón Subir plugin (arriba).
  4. Elegí el archivo ZIP y pulsá Instalar ahora.
  5. Cuando termine, pulsá Activar plugin.

(Guía genérica equivalente en WordPress.org: Managing Plugins, sección sobre subir plugins.)

3. Comprobar que quedó bien

  • En Plugins → Plugins instalados deberías ver OSINT Deck como activo.
  • En el menú lateral debería aparecer una entrada OSINT Deck.

4. Mostrar el mazo en el sitio

  1. Páginas o Entradas → Añadir nueva (o editá una existente).
  2. En el contenido pegá: [osint_deck] o [osint_deck_search] (ambos muestran el buscador del mazo).
  3. Publicá o actualizá la página y abrila: deberías ver la interfaz del mazo.
Si al activar aparece un error de “autoload” o “vendor”: el ZIP no era el de release completo o se subió una carpeta sin dependencias. Volvé a descargar el ZIP desde Releases o usá un paquete construido con composer install --no-dev.

Instalación y actualizaciones

En esta sección. Requisitos de servidor, Composer, ZIP con vendor/ y actualizaciones remotas. Audiencia: quien despliega el plugin (administrador o DevOps). Después: Composer / WP-CLI si trabajás desde el código, o saltá a Escritorio WP si ya instalaste.

En la práctica: descargá el ZIP de una release del repo OsintDeck/OsintDeck (debe incluir la carpeta vendor/). En wp-admin andá a Plugins → Añadir nuevo → Subir plugin, elegí el ZIP, instalá y Activá. Para una guía con más detalle y capturas, usá Instalar el plugin (modo fácil) o la Guía rápida. Si desarrollás el código: cloná el repositorio y ejecutá composer install antes de empaquetar o subir por FTP (véase Composer y WP-CLI).

Requisitos de runtime

Valores declarados en la cabecera del plugin (osint-deck.php):

  • WordPress: 5.8 o superior (Requires at least). Las ramas 6.x actuales son el entorno objetivo en producción.
  • PHP: 7.4+ (Requires PHP); se recomienda 8.x alineado al soporte del hosting.
  • Base de datos: la misma instancia MySQL/MariaDB del sitio; el plugin crea tablas propias en la activación y migraciones versionadas.
  • Composer: obligatorio en el workspace de desarrollo para generar vendor/. Los ZIP de GitHub Releases deben incluir vendor/autoload.php para instalación sin CLI en el servidor.
  • Cliente: navegador actual (ES6+, fetch/AJAX).
Sin vendor/autoload.php el bootstrap fallará. Reinstalá desde el release o ejecutá composer install --no-dev --optimize-autoloader antes de empaquetar.

Flujos de despliegue

  • Operaciones: subida ZIP vía wp-admin — Instalación paso a paso.
  • Desarrollo / CI: clon del repo + Composer — Composer y WP-CLI.

Actualizaciones remotas (Plugin Update Checker)

El bootstrap registra plugin-update-checker contra https://github.com/OsintDeck/OsintDeck. Los tags y el header Version deben alinearse. Desactivación global: 

define( 'OSINT_DECK_DISABLE_REMOTE_UPDATES', true );

Publicar el ZIP como asset en cada release mejora la experiencia de actualización en el escritorio.

Qué puede hacer un administrador (escritorio WordPress)

Todo esto está en el menú OSINT Deck del escritorio (submenús según la versión: herramientas, ajustes, métricas, etc.).

Tareas habituales

  • Gestionar herramientas del mazo: alta, edición o borrado; importar/exportar JSON; categorías e iconos.
  • Ajustes generales y diseño: tema claro/oscuro, barra fija, textos de tarjetas de ayuda, crisis o comunidad.
  • Dominios y TLDs: lista de sufijos válidos y TLDs personalizados.
  • Seguridad y autenticación: Turnstile, OAuth Google para visitantes.
  • Métricas: uso agregado para ver qué herramientas se usan más.
  • Logs y soporte: diagnóstico y mantenimiento según opciones del plugin.
Permisos: suelen ver estas pantallas los usuarios con rol de administrador (o quien pueda gestionar plugins). Los visitantes del sitio público no.

Qué puede hacer un visitante en el mazo (web pública)

Estas acciones están en la página donde insertaste el shortcode. No hace falta ser administrador de WordPress.

  • Escribir o pegar en la barra: el texto se analiza y el mazo muestra herramientas acordes al tipo de dato detectado (dominio, IP, correo, etc.).
  • Filtrar herramientas: categorías, tipo de acceso, licencia — reducen la lista en vivo.
  • Abrir una herramienta: enlaces principales o vista embebida cuando el sitio lo permite.
  • Copiar o pegar desde el portapapeles: según los botones que muestre tu versión junto a la barra.
  • Favoritos o “me gusta” (si está habilitado): puede pedirse inicio de sesión con Google si tu sitio lo configuró.
  • Inicio de sesión con Google: si el administrador activó SSO, permite sesión propia del plugin (favoritos, historial, etc.) sin usar cuentas de edición del sitio.
  • Reportar un problema en una herramienta: según configuración y protección anti-abuso (p. ej. Turnstile).
  • Ayuda, comunidad o avisos: textos y enlaces que el administrador define en el panel del plugin.

Shortcodes

[osint_deck] y [osint_deck_search]

Renderizan el buscador / mazo. El nombre osint_deck se mantiene por compatibilidad.

[osint_deck_search]
[osint_deck]
[osint_deck category="dominios" access="gratuito" limit="20"]

Atributos: category (nombre o código), access (valor en metadatos), limit (si es > 0 recorta la lista; -1 sin límite).

[osint_deck_cards]

Rejilla estática de herramientas.

[osint_deck_cards category="dns" limit="10" orderby="clicks" order="DESC"]

Atributos: category, tag, limit, orderby (title | clicks), order (ASC|DESC).

Tip: Usa osint_deck_cards cuando solo quieras listar herramientas sin el buscador completo.

Tema y barra de búsqueda

El aspecto del mazo (claro / oscuro / según sistema) y el comportamiento de la barra se controlan desde OSINT Deck → Ajustes, pestañas de diseño o general según tu versión.

  • Tema: modo automático (preferencia del sistema del visitante) o fijo; a veces hay selector en el DOM del tema (data-site-skin, clases en <html>, etc.) para alinear con tu plantilla.
  • Barra fija: opción para mantener la barra de búsqueda visible al hacer scroll; puede incluir offset en píxeles para no tapar el header del tema.
  • Caché de assets: CSS y JS se etiquetan con OSINT_DECK_VERSION para forzar recarga al actualizar el plugin.
Plantillas: si la barra queda debajo del menú del tema, probá el offset o la opción de barra fija; cada tema tiene alturas distintas de cabecera.

Inicio de sesión con Google

En esta sección. OAuth de Google para visitantes del mazo (no usuarios wp-admin), flujo de token y datos guardados en tablas del plugin. Antes: Turnstile si lo tenés activo (afecta el login AJAX). Después: Historial y favoritos.

Opcional en OSINT Deck → Ajustes → Integraciones y Seguridad (misma pestaña que Turnstile y GitHub). Permite que visitantes del front (no administradores del escritorio WP) tengan una identidad estable para funciones del mazo sin crearles usuario WordPress.

¿Por qué integrar Google?

El mazo funciona sin login: búsqueda y catálogo son públicos. La integración OAuth aporta valor cuando querés:

  • Favoritos y “me gusta” persistentes entre dispositivos, ligados a una cuenta en lugar de solo al navegador.
  • Historial de actividad asociado al perfil del deck (tablas propias del plugin).
  • Reportes con comentario: un visitante anónimo puede marcar una herramienta rota; si inicia sesión, puede añadir un mensaje al reporte (política implementada en UserEvents / ToolReports).
  • Borrado de cuenta y datos coherentes con RGPD/privacidad sin tocar wp_users.

Los perfiles viven en tablas del plugin (DeckUsers y relacionadas), no reemplazan al sistema de usuarios de WordPress para administración del sitio.

Flujo técnico resumido

  1. El visitante pulsa el botón de Google en la barra del mazo; el navegador obtiene un ID token (Google Identity Services).
  2. El cliente envía ese token por AJAX a osint_deck_auth_google con el nonce público. Si Turnstile está activo, también envía el token de verificación.
  3. El servidor valida el token contra https://oauth2.googleapis.com/tokeninfo y comprueba que el aud coincida con tu Client ID.
  4. Con email y sub válidos, se hace upsert del usuario del deck y se fija la cookie de sesión osd_user.

Configuración en Google Cloud

Necesitás un proyecto, pantalla de consentimiento OAuth (típicamente tipo externo) y un ID de cliente OAuth 2.0 de aplicación Web. En el plugin también podés guardar el Client Secret según la guía del panel (algunos flujos lo usan; el intercambio vía tokeninfo del ID token es el camino documentado en código para la sesión del deck).

  • Origen JavaScript autorizado: la URL base del sitio donde está el shortcode, sin barra final (el propio wp-admin del plugin lo recuerda en el texto de ayuda).
  • URI de redirección: para el botón “Sign in with Google” muchas veces basta el origen; podés añadir la misma URL por compatibilidad.

En el escritorio de WordPress, el menú del plugin incluye un desplegable paso a paso (“Google SSO”) en Integraciones y Seguridad: usalo como checklist junto con esta documentación.

Endpoints AJAX relacionados

  • osint_deck_auth_google — validar ID token y abrir sesión.
  • osint_deck_get_user — estado de sesión y listas (favoritos, reportes abiertos, agradecimientos pendientes).
  • osint_deck_logout — cerrar sesión del deck.
  • osint_deck_delete_my_account — borrado de datos del usuario del deck (con confirmación estricta en POST).

Reportes de herramientas (bandera en el mazo)

Cuando un enlace del catálogo está caído, desactualizado o es inapropiado, el visitante puede marcar la herramienta con el control tipo bandera en la carta. Eso alimenta la cola que ves en el escritorio como OSINT Deck → Reportes (admin.php?page=osint-deck-tool-reports, pantalla ToolReportsAdmin.php).

Qué se guarda y quién puede hacer qué

  • Usuario con sesión Google en el deck: el reporte queda asociado a su user_id en las tablas del plugin. Puede dejar un comentario opcional al reportar (texto saneado y acotado en longitud).
  • Visitante anónimo: puede reportar sin comentario; el sistema usa una huella enviada por el cliente (fp) y la persiste como hash (ToolReports::fp_hash) para no duplicar reportes del mismo navegador hasta que se cierre el ticket.
  • Toggle: volver a pulsar la bandera retira el reporte abierto (misma política de usuario o de huella).

Los inserts y bajas pasan por la acción unificada osd_user_event con evento report / report_tool (UserEvents.php), con verificación Turnstile si está habilitado. El contador visible de reportes en la ficha de la herramienta se actualiza vía el repositorio (increment_reports / decrement_reports).

Lado administración

En Reportes ves herramientas con reportes abiertos. Al marcar como reparado:

  • Se cierran los reportes abiertos de esa herramienta y se encola un agradecimiento para quienes habían reportado (ReportThanks).
  • El usuario verá un mensaje de gracias en el mazo hasta que lo descarte (acción osint_deck_dismiss_report_thanks).
  • GitHub (opcional): al cerrar reportes podés generar un issue en el repo; la integración se documenta en GitHub e issues de reparación (sección propia en este manual).

Lectura de estado sin Turnstile

La acción osint_deck_report_state solo devuelve qué herramientas tiene reportadas o pendientes de agradecimiento el visitante (por usuario o huella); no modifica datos y en el código actual no pasa por Turnstile, a diferencia del envío del reporte vía osd_user_event.

Moderación: el reporte es señal para el equipo, no prueba automática: conviene revisar la URL, el contexto y duplicados antes de dar por cerrado el caso.

GitHub e issues de reparación

En esta sección. Integración opcional para crear issues en GitHub cuando un administrador marca una herramienta como reparada en OSINT Deck → Reportes. Antes: entender el flujo de la bandera en Reportes de herramientas. Código: GitHubRepairIssueNotifier.php.

Es una función opcional y voluntaria: sirve para que el equipo del sitio comparta con el repositorio upstream (por ejemplo OsintDeck/OsintDeck) qué herramienta se corrigió, qué decían los reportes y un volcado JSON importable.

Configuración en WordPress

  1. Andá a OSINT Deck → Ajustes → Integraciones y Seguridad (pestaña tab=auth en la URL de ajustes).
  2. En la sección GitHub (repo público) (#osint-deck-github-section): activá la casilla, indicá el repo en formato owner/repo (por defecto suele ser OsintDeck/OsintDeck) y pegá un token de acceso personal con permiso para crear issues en ese repositorio (en la UI del plugin se recomienda un token fine-grained; el asistente paso a paso está en el mismo panel).
  3. Alternativa al campo del formulario: variable de entorno OSINT_DECK_GITHUB_ISSUES_TOKEN en el servidor (el código la lee si la opción en BD está vacía).
  4. GitHub Enterprise u otra API: podés definir OSINT_DECK_GITHUB_API_URL en wp-config.php para cambiar la base de la API respecto de https://api.github.com.

Uso desde OSINT Deck → Reportes

Cuando resolvés reportes abiertos de una herramienta y enviás el formulario de “reparado”, si GitHub está bien configurado aparece la opción de informar al desarrollador (report_to_developer). Si la marcás, el plugin hace POST a la API de GitHub y crea un issue cuyo título sigue el patrón [OSINT Deck] Reparada: … (host del sitio).

El cuerpo del issue incluye, entre otras cosas: URL del sitio, versión del plugin, nombre y slug de la herramienta, enlace a edición en wp-admin, quién cerró el ticket, cantidad de reportes y de agradecimientos, lista de lo reportado (fecha, usuario WP o “Anónimo”, mensaje si lo hubo), nota opcional del administrador sobre cómo se resolvió, y un bloque json con el estado actual de la herramienta (mismo criterio que exportación; si es muy grande se trunca con aviso en el texto). Si la API falla, el panel muestra el error y el mensaje del plugin indica revisar la configuración en Ajustes.

Si GitHub no está configurado y aun así marcás informar al desarrollador, verás un aviso para completar la sección de GitHub en Integraciones y Seguridad (el enlace directo desde Reportes apunta a admin.php?page=osint-deck-settings&tab=auth#osint-deck-github-section).

Aviso en pantalla Reportes

Si la integración no está lista, el plugin puede mostrar un recordatorio de colaboración en Reportes; se puede descartar y reactivar desde los propios ajustes de GitHub en Integraciones y Seguridad (opción interna osint_deck_github_collab_nudge_dismissed).

Token y permisos: el token es credencial sensible (equivalente a contraseña para la API). No lo compartas ni lo subas a repositorios públicos. Si se filtra, revocalo en GitHub y generá uno nuevo. Conviene un token mínimo (solo issues: write en el repo que elijas).

Seguridad y rendimiento

En esta sección. Turnstile, TLDs, logs y coste de las rutas públicas. Audiencia: integradores y administradores preocupados por abuso y rendimiento. Relacionado: Google, Reportes, GitHub (issues), Dominios / TLDs.

Integración con Cloudflare Turnstile

Aclaración: no hace falta que el sitio WordPress esté “detrás de” el proxy Cloudflare para usar esta función. El plugin integra el producto Turnstile (verificación humana / anti-bot de Cloudflare) como widget y verificación en servidor, similar conceptualmente a reCAPTCHA pero con la política de privacidad y UX de Cloudflare.

Pasos típicos:

  1. En Cloudflare Dashboard, abrí Turnstile y creá un sitio/widget (modo managed o no interactivo según prefieras).
  2. Copiá la Site Key (pública) y la Secret Key (privada).
  3. En WordPress: OSINT Deck → Ajustes → Integraciones y Seguridad (Google, Turnstile y GitHub), activá Turnstile y pegá ambas claves. Guardá los cambios.

El servidor valida el token con https://challenges.cloudflare.com/turnstile/v0/siteverify (Turnstile.php). El front envía el token en cf_turnstile_response (o variante con guión). Si Turnstile está desactivado o faltan claves, la verificación no se exige y las rutas siguen (útil en entornos de desarrollo local).

Qué protege cuando está activo (resumen): búsqueda del mazo, seguimiento de clics, comprobación de iframes, bloqueo de iframe en caché, login y logout con Google, borrado de historial, vaciar favoritos, borrar cuenta, cierre de mensajes de agradecimiento por reportes, y los eventos públicos unificados osd_user_event (favoritos, me gusta, reporte de herramienta, etc.). Algunas lecturas de estado (p. ej. sesión actual o listado de historial) no pasan por Turnstile; revisá el código de AjaxHandler.php y UserEvents.php si necesitás el detalle exacto por acción.

Documentación oficial: Cloudflare Turnstile.

Validación de dominios y TLD

La detección “dominio” depende de listas IANA mantenidas por TLDManager y tareas programadas (véase Dominios y TLDs). Esto reduce falsos positivos y evita consultas externas por cada pulsación en el deck.

Auditoría y logs

src/Infrastructure/Persistence/LogsTable.php define la tabla {prefix}osint_deck_logs (mensaje, nivel, contexto serializado, marca temporal). Complementa el componente Infrastructure/Service/Logger.php para trazas operativas y depuración sin volcar datos sensibles al front.

Superficie AJAX y coste

  • Nonces de WordPress en acciones públicas y de administración.
  • Iframes: comprobación por lotes con techo de URLs por petición y resultados cacheados en transientes para limitar latencia y carga sobre orígenes externos.
  • Capacidades (current_user_can) en rutas de mantenimiento e importación.

Dominios y TLDs

El motor valida dominios usando una copia local de la lista oficial IANA. Un cron del plugin refresca esa lista para no depender de una petición en cada búsqueda.

  • Fuente IANA: tlds-alpha-by-domain.txt almacenado en opciones de WordPress.
  • Cron semanal: acción programada osint_deck_update_tlds.
  • TLDs personalizados: campo o lista en OSINT Deck → Ajustes → Dominios / TLDs para laboratorios o dominios especiales.
  • Uso en runtime: el detector de tipo “dominio” consulta esos datos antes de marcar un token como FQDN válido.

Historial, favoritos y privacidad

Estas capacidades enlazan el front con admin-ajax.php. El flujo de la bandera de reporte está explicado en detalle en Reportes de herramientas. Aquí el listado de acciones relacionadas.

Requieren nonces válidos; muchas escrituras exigen Turnstile si está activo (véase Turnstile).

  • Historial de búsqueda: osint_deck_get_history, osint_deck_clear_history.
  • Favoritos: osint_deck_clear_favorites y eventos relacionados vía osd_user_event.

Arquitectura del sistema

En esta sección. Mapa de carpetas bajo src/ y separación de capas (Domain, Infrastructure, Presentation). Audiencia: desarrolladores y quienes mantienen el código. Antes: conviene haber leído la puesta en marcha; después: Motor de decisiones y Referencia AJAX.

El código bajo convenciones PSR-4 vive en src/ y se organiza por capas para separar reglas de negocio, infraestructura y presentación.

  • Core/ — Bootstrap.php coordina el ciclo de vida del plugin: instancia repositorios, servicios de dominio, registra hooks de WordPress, menús admin, shortcodes, AJAX y migraciones de esquema.
  • Domain/ — Lógica de negocio independiente del framework: Service/DecisionEngine.php, Service/InputParser.php, Service/NaiveBayesClassifier.php e interfaces en Repository/ (contratos de herramientas y categorías).
  • Infrastructure/ — Persistencia (Persistence/*.php: tablas personalizadas, repositorios concretos), integraciones (Service/TLDManager.php, Auth/), seguridad (Security/Turnstile.php) y utilidades (logger, iconos, respaldos).
  • Presentation/ — Admin/ (ajustes, métricas, herramientas, import/export), Frontend/Shortcodes.php y Api/ (p. ej. AjaxHandler.php, eventos de usuario).

Los datos semilla y configuraciones estáticas complementarias residen en data/ (JSON de herramientas, categorías, entrenamiento y dorks), alimentando un modelo data-driven sin recompilar PHP para ajustes de catálogo en entornos administrados.

Extensión: nuevas capacidades deben respetar la frontera Domain ↔ Infrastructure (reglas sin SQL directo en dominio) y usar hooks de WordPress para enganchar UI y AJAX.

Motor de decisiones (Decision Engine)

El cerebro operativo es src/Domain/Service/DecisionEngine.php. Recibe la consulta del usuario y devuelve estructura lista para el front: modo de operación, entradas detectadas y conjunto de herramientas/cartas relevantes.

Flujo de procesamiento

  1. Entrada — Texto libre desde la barra del deck (shortcode público).
  2. Parsing — InputParser.php aplica patrones (regex) y validación asistida por TLDManager para distinguir IP, dominio, correo, hash, URL, ASN, teléfono, wallet, etc.
  3. Modo — Sin entradas estructuradas: MODE_CATALOG (catálogo filtrable). Con entradas: MODE_INVESTIGATION (activación contextual de herramientas).
  4. Clasificación y ranking — El repositorio de herramientas aporta metadatos; opcionalmente interviene NaiveBayesClassifier para sugerir mazos en función de rasgos del input.
  5. Salida — Colección normalizada consumida por JavaScript vía AJAX (admin-ajax.php, acción osint_deck_search u otras definidas en AjaxHandler).

Clasificador Naive Bayes (¿qué es y para qué está?)

En este proyecto “bayesiano” se refiere al clasificador Naive Bayes implementado en src/Domain/Service/NaiveBayesClassifier.php. Es un modelo probabilístico clásico de NLP: a partir de ejemplos de texto etiquetados, estima qué tan probable es que una frase nueva pertenezca a una categoría (por ejemplo intención de ayuda, tipo de dato técnico, saludo, etc.). “Naive” indica que se asume independencia entre palabras; simplifica el cálculo y suele funcionar bien cuando las palabras clave son buenas señales, como en consultas tipo dorks o OSINT.

Orden real en el motor: primero InputParser intenta detectar tipos con expresiones regulares y validaciones (dominio con TLD, IP, hash, URL…). Solo si no hubo coincidencias, entra el Naive Bayes: clasifica el texto libre y, si la predicción es aceptada, se traduce a un tipo interno compatible con el resto del DecisionEngine. Así las regex cubren lo estructurado y el clasificador refuerza lenguaje más abierto o ambiguo.

Datos de entrenamiento: semilla en data/training_data.json; en producción el modelo y ejemplos pueden persistir en opciones de WordPress. Los administradores pueden ampliar el entrenamiento desde OSINT Deck → Entrenamiento IA (Naive Bayes) (AiTrainingManager.php), alineado con backups que incluyen el estado del clasificador (DeckFullBackup).

No es ChatGPT: es un clasificador ligero en PHP (y espejo en JS para el cliente donde aplica), pensado para latencia baja y hosting compartido, no para generar texto.

Modelo data-driven

El catálogo no está hardcodeado en el motor: se nutre de definiciones persistidas (importables desde JSON en data/ como tools-defaults.json, categories-defaults.json, training_data.json, etc.) y de filas en tablas propias tras la activación del plugin. Esto permite actualizar herramientas sin tocar el núcleo del clasificador salvo nuevos tipos de entrada.

Cron y tareas programadas

WordPress dispara estos hooks según la cola de wp-cron.php (en muchos hostings se ejecuta al visitar el sitio; en producción conviene cron real del sistema apuntando a wp-cron.php).

  • osint_deck_update_tlds — actualización periódica (semanal) de la lista IANA de TLDs.
  • osint_deck_daily_cleanup — limpieza diaria de datos temporales o mantenimiento ligero según la versión del plugin.

AJAX (panel técnico)

Todas las acciones van contra wp-admin/admin-ajax.php (o admin-ajax.php en la raíz de admin) con el parámetro action igual al nombre listado. El front envía nonces para validar el origen.

Públicas (o mixtas): búsqueda y motor osint_deck_search, seguimiento de clics osint_deck_track_click, comprobación de embeds osint_deck_check_iframe, bloques de reporte osint_deck_report_block, autenticación Google, historial, favoritos, osd_user_event, y acciones de reportes citadas en Historial y favoritos.

Solo administración: mantenimiento de iconos (osint_deck_force_download_icons, osint_deck_list_remote_icons, osint_deck_save_manual_icons), import/export de herramientas (osint_deck_import_tool, osint_deck_export_tool), sugerencias para métricas osint_deck_metrics_tool_suggest, etc. Requieren usuario con capacidad adecuada y nonce de admin.

Depuración: con las herramientas de red del navegador (pestaña Network) filtrá por admin-ajax.php y revisá el cuerpo de la respuesta si una carta o el login fallan en silencio.

Sobre el Proyecto

OSINT Deck es un plugin para WordPress que centraliza y organiza herramientas de investigación en fuentes abiertas. El usuario ingresa un dato (correo, dominio, IP, hash, etc.) y el sistema lo clasifica automáticamente para activar los recursos pertinentes —vista embebida o acceso externo con parámetros cargados— usando una lógica de mazos y cartas que facilita el flujo de trabajo.

El proyecto fue desarrollado en la Licenciatura en Ciberseguridad de la Universidad Nacional Raúl Scalabrini Ortiz (UNSO), Argentina, tomando como referencia la experiencia del blog OSINT.com.ar. Hoy está publicado como software libre y puede instalarse en cualquier WordPress. Para implementación interna véase Arquitectura del sistema.

Mantente actualizado: Visita osint.com.ar para leer artículos sobre técnicas OSINT, herramientas, casos de estudio y las últimas novedades en ciberseguridad.

Características Principales

Detección automática del tipo de dato

El motor de decisión analiza el texto ingresado. Entre otros formatos:

  • Email, Dominio / subdominio, URL, IP v4 / v6
  • ASN, MAC, UUID, Hashes (MD5, SHA1, SHA256)
  • Teléfonos, Coordenadas, Wallets BTC / ETH
  • Claves PGP, Archivos conocidos, Username / alias
  • Nombre completo, ZIP / Código postal, Paquetes com.*.*

Mazo dinámico de herramientas

  • Cartas por herramienta con enlaces y metadatos
  • Filtros por categoría, acceso y licencia
  • Embebidos con comprobación por AJAX cuando aplica
  • Reportes, favoritos y “me gusta” según sesión
  • Cartas de ayuda, crisis y comunidad (textos editables en admin)

Para gráficos, filtros y detalle de implementación véase Métricas y panel de administración.
